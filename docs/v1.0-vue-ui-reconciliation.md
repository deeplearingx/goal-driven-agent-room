# v1.0 — Vue UI 接入对齐审计

> 状态：**审计完成 2026-06-14**，用于 PLAN.md §6.1 / §6.2 决策前的形状对账。
> 不是一份"已批准的迁移方案"——产出**待决问题**与**推荐路径**，等用户拍板。

## 目的

PLAN.md §6.1 写明 v1.0 的 UI 部分是「把 hermes-web-ui 的 agent-room 客户端抽出来
重接到本服务」。在动 Vue 一行代码之前，先把两端的 API 形状钉在一起看清楚。

## 两端清单

### 本仓库 server（[agent_room/server/api.py](../agent_room/server/api.py)）

5 个路由，**任务为根**：

| 方法 | 路径 | 行为 |
|------|------|------|
| `GET`  | `/healthz` | liveness |
| `POST` | `/tasks` | 同步跑一个任务，返回 `TaskResult` |
| `POST` | `/tasks/stream` | SSE 推 LangGraph 事件流 |
| `GET`  | `/tasks/{task_id}` | 快照 |
| `POST` | `/tasks/{task_id}/resume` | 续跑 `awaiting_user` 任务，body `{"decision": str}` |

[`schemas.py`](../agent_room/schemas.py)：`TaskRequest` / `TaskResult` / `Artifact` /
`Event` / `ReviewerDecision` / `PlannerGateOutput` / `FocusCheck`。状态枚举仅 4 个：
`completed | failed | awaiting_user | running`。

SSE 事件（[`events.py::format_stream_event`](../agent_room/events.py)）：
`task_started` / `node_start` / `node_end` / `token` / `task_finished` / `task_error`。

无 session 概念。无 run 与 task 的分层。一次 `POST /tasks` 就是一次 task；revision
表现为 `TaskResult.rounds` + `Artifact.round`。

### hermes-web-ui 客户端（[`packages/client/src/api/hermes/agent-room.ts`](../../hermes-web-ui/packages/client/src/api/hermes/agent-room.ts) + [`stores/hermes/agent-room.ts`](../../hermes-web-ui/packages/client/src/stores/hermes/agent-room.ts)）

**会话为根**，~25 个路由（前缀 `/api/agent-room`）。摘要：

| 资源 | 端点（节选） |
|------|--------------|
| sessions | `POST/GET /sessions`、`GET /sessions/{id}`、`DELETE /sessions/{id}`、`GET /sessions/{id}/metrics` |
| messages | `GET/POST /sessions/{id}/messages` |
| tasks    | `GET/POST/DELETE /sessions/{id}/tasks`、`PATCH .../status`、`POST .../retry`、`POST .../deliver` |
| review   | `POST /sessions/{id}/tasks/{tid}/review` |
| workflow | `POST .../workflow`、`POST .../workflow/start` |
| events   | `GET /sessions/{id}/events`（workflow events）、`GET /sessions/{id}/run-events`、`GET /runs/{rid}/events` |
| runs     | `GET /sessions/{id}/runs`、`GET /runs/{rid}`、`GET /runs/{rid}/role-runs` |
| artifacts| `GET /sessions/{id}/artifacts`、`GET .../tasks/{tid}/artifacts`、`DELETE .../artifacts/{aid}` |
| role bindings | `GET/PUT/DELETE /sessions/{id}/role-bindings/{role}` + profile preview |
| session config | `GET/PATCH /sessions/{id}/config` |

**实体**（节选）：
- `AgentRoomSession{id, name, autoDeliveryEnabled, createdAt, updatedAt}`
- `AgentRoomTask` —— 状态 12 个：`created / planned / assigned / in_progress /
  submitted_for_review / review_passed / review_rejected / revision_required /
  delivering / completed / failed / need_user_decision`
- `AgentRoomMessage` —— `senderRole` 包括 `'user'` 与 `conversation` Agent
- `AgentRoomRun{id, sessionId, taskId, status, runnerName, ...}` —— **task 之外
  的执行单位**；状态 4 个：`queued / running / completed / failed`
- `AgentRoomRoleRun{runId, role, phase, profileName, status, metadata, ...}`
  —— per-role 执行记录，rolerun 状态包含 `skipped`
- `AgentRoomRoleBinding{role, profileName, provider, model}` —— 不只是 model id，
  还要绑 profile name
- `AgentRoomRunEvent`、`AgentRoomWorkflowEvent` —— 两套不同事件流
- `AgentRoomSessionMetrics` —— 7 个汇总比率指标

**通信方式**：纯 polling，3s `setInterval`，没有 `EventSource`。

5 个 role：`conversation / planner / developer / reviewer / delivery`（多一个
`conversation`）。

## 落差表

| 维度 | 本仓库 server | hermes-web-ui 客户端 | 差距等级 |
|------|---------------|---------------------|----------|
| 资源根 | task | session ⊃ tasks ⊃ runs ⊃ roleRuns | **架构级** |
| 路由前缀 | `/` 直接 `/tasks` | `/api/agent-room/...` | 低（前缀加一下） |
| 状态机 | 4 状态 | 12 状态 | **高**（语义不重合） |
| role 数 | 4 | 5（多 `conversation`） | 中 |
| revision 模型 | `Artifact.round` 在单 task 内 | `revisionRound` 字段 + `parentTaskId` 链 | 中 |
| 实时通信 | SSE（已有） | 3s polling（无 SSE 客户端） | **高**（两端选型不同） |
| Run / RoleRun 表 | 无 | 一等公民，前端处处依赖 | **架构级** |
| Profile / RoleBinding | `RoleBindings` per-process 装配 | per-session DB 持久化 + 命名 profile | **高** |
| Metrics | 无 | 7 个汇总比率 + Prometheus 友好 | 中 |
| Artifact 持久存储 | LangGraph checkpointer 内置 | 独立 `artifacts` 表 + `storageUrl` 外链 | 中 |
| Auto-delivery 开关 | 总是发 | per-session toggle | 低 |

## 路径选项

> 三选一前先回答两个根本问题（见末尾"待决"）。

### A — 服务端长出 Session/Run shim（兼容客户端形状）

在 [`agent_room/server/api.py`](../agent_room/server/api.py) 之外加一个
`agent_room/server/compat_v1.py`，挂 `/api/agent-room/...` 前缀，把 hermes-web-ui
现成的所有调用映射到本仓库的 task 模型。Session 退化为「一组 task 的容器」，
Run/RoleRun 由 LangGraph stream events 派生。前端几乎不动，省 1-2 周 Vue 工作。

**代价**：
- 多维护一个 v1 兼容路由层（约 800-1200 行 FastAPI + 一张 `sessions` 表 + 一个
  「checkpointer 事件 → run-event 行」的投影器）。
- 前端的 `setInterval(3s)` 完全照搬——本仓库的 SSE 优势没用上。
- 12 状态 ↔ 4 状态映射要明文（如 `revision_required → running` ）写进 ADR，
  避免前端误解。
- "Profile" 概念在本仓库不存在，要么补一张 `role_profiles` 表存 model + key 映射，
  要么从客户端删掉 RoleBindingModal——前者改后端、后者改前端。

### B — 写新 Vue（贴本仓库 4-状态 + SSE 模型）

抽 hermes-web-ui 的可视化资产（`AgentRoomTimelineView` / `AgentRoomMessageList` /
office scene 等纯展示组件），扔掉所有 Pinia store + API 客户端，按 task-rooted +
SSE 重写一个最小 SPA。

**代价**：1-2 周 Vue 工作，但形状正、长期维护成本最低。

### C — 混合（推荐）

服务端加 **薄** session adapter 解决前端"以 session 列出所有 task 历史"的能力刚需，
其它 25 个路由按需在本仓库已有形状之上 facade（不为对齐而对齐）；前端选择性弃用
不再返回数据的字段，并在 `EventSource('/tasks/stream')` 上**新增** SSE wiring 替
代 polling（保留 polling 作为降级）。

落地要点：
1. **新加路由**（最小集，~250 行 FastAPI）：
   - `GET /api/agent-room/sessions` / `POST` / `GET /sessions/{id}`
   - `GET /api/agent-room/sessions/{id}/tasks`（关联表）
   - `POST /api/agent-room/sessions/{id}/tasks` → 透传到 `service.run`
   - `POST /api/agent-room/sessions/{id}/tasks/{tid}/resume` → 透传 resume
2. **保留主路径不变**：`POST /tasks`、`POST /tasks/stream`、`GET /tasks/{id}` 不动
   （SemVer 1.0 主推 task-rooted，session 是兼容糖）。
3. **SSE 客户端补强**：新增 `useAgentRoomTaskStream(taskId)` composable，封 `EventSource`
   订阅 `/tasks/stream`；前端新组件用它，老组件继续 3s poll。
4. **状态映射明文 ADR**：在 [`docs/adr/`](adr/) 新增 ADR-0011 「12-state UI ↔ 4-state
   server」，把 mapping 写死防止后续踩坑。
5. **runs / roleRuns 不补**：客户端这块的 UI（RunsView / RoleRunCards）改成读
   `Event[]` 派生展示；要抢救 RunsView 就接 `/tasks` 列表 + `Event` 累计。
6. **Profile / RoleBinding API 不补**：让 [`AgentRoomRoleBindingModal`](../../hermes-web-ui/packages/client/src/components/hermes/agent-room/AgentRoomRoleBindingModal.vue)
   改读 server 暴露的"环境模型"（`AGENT_ROOM_{ROLE}_MODEL` env），或下版本接入。

**预算估计**：~3-5 天后端 + ~2-3 天前端改造（vs Option A ~10 天后端、Option B
~10-14 天前端）。

## 待决（用户拍板）

D1. **Session 是否进入本仓库的一等概念？**
   - 进 → 跟 PLAN.md §0 「task 为根」的目前事实正面冲突，要补一张 SQL 表
     ([`sessions`](#)) 与生命周期（创建 / 删除 / 多 task 索引）。
   - 不进 → Option C（兼容糖路由）即可。

D2. **前端的 12 状态语义保留还是收敛到 4？**
   - 保留 → Option A 必走，状态机映射逻辑跟着加。
   - 收敛 → 简化所有 status 显示组件（`AgentRoomTaskPanel` / `AgentRoomTimelineView`），
     Option B 或 C 都可。

D3. **Realtime 通道选 SSE 还是保留 polling？**
   - 本仓库已经有 `/tasks/stream`，前端没用——白扔了 v0.4 的功夫。建议 Option C
     的"新组件 SSE / 老组件 polling 兼容并存"。

D4. **Profile / Role Binding 是否进 v1.0？**
   - hermes-web-ui 把它做成 per-session 的命名 profile + provider/model 双重 override。
     本仓库 v0.5 是 dataclass + env。两套并存意味着补一张 `role_bindings` 表。
     建议**推后**到 v1.1，v1.0 只跑 env 配置。

## 推荐结论

走 **Option C**：

- 后端补 `/api/agent-room/sessions` 薄壳（路由 ~250 行 + 一张 `sessions` 表，无
  Run/RoleRun/Profile）。
- 前端 SSE 客户端用 `EventSource('/tasks/stream')` 跑新建/查看入口；其余视图
  保留 polling。
- ADR-0011 钉死状态机映射 + session 语义。
- D1/D2 倾向"不进 / 收敛 4 状态"，但有形状对齐成本，需用户确认；D3 推荐 SSE，
  D4 推荐推后 v1.1。

回答这四问后，PLAN.md §6.1 / §6.2 拆 v1.0 §6.1.x 子任务卡。
