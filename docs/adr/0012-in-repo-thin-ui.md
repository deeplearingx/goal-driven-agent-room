## ADR-0012: In-repo thin UI (drop hermes-web-ui reuse)

**Status**: Accepted (2026-06-23, v1.0 §6.1)

**Supersedes**: parts of [ADR-0011](0011-vue-ui-state-mapping.md) — §6.1.4-§6.1.7
front-end migration tasks. ADR-0011's status-mapping table is still the
authoritative 12→4 contract; only the *consumer* changes.

**Companion**: [v1.0-vue-ui-reconciliation audit](../v1.0-vue-ui-reconciliation.md)
· [ADR-0007 — borrow-not-integrate hermes](0007-borrow-not-integrate-hermes.md)

## Context

§6.1.1-§6.1.3 (sessions thin shell + ADR-0011 + `/healthz` role map) landed
2026-06-22 to make hermes-web-ui's Vue client mountable on this server. The
remaining §6.1.4-§6.1.7 work (~4.5d) is all in `/home/ly/hermes-web-ui`:

- §6.1.4: `useAgentRoomTaskStream` SSE composable (1d)
- §6.1.5: rewrite `stores/hermes/agent-room.ts` polling → SSE (1.5d)
- §6.1.6: 12→4 status panel + delete `AgentRoomRunsView` /
  `AgentRoomRoleBindingModal` / `AgentRoomSessionMetrics*` (1d)
- §6.1.7: e2e smoke + reconciliation doc (1d)

The form of that work — *delete 40% of an existing client + rewrite the
store + collapse 12 statuses to 4* — is closer to a rewrite than to reuse.
The Option C "harder cut" was the right call against the v0.1 baseline of
"reuse the SPA verbatim", but the cost has converged to the cost of building
a thin UI from scratch.

Two further pressures argue for a pivot:

1. **Independence story leaks at the use-site.** The strongest claim of
   this project (ADR-0007) is that `rm -rf /home/ly/hermes-agent` keeps
   `pytest -q` green. But anyone who wants the UI still has to clone
   hermes-web-ui. End-to-end use is not independent.
2. **Cross-repo sync tax.** Every backend schema or SSE event change has
   to land in two repos with different conventions, build chains, and
   review queues. Linear maintenance cost > one-time UI build cost.

The user agreed to the pivot 2026-06-23 after a four-option comparison
(A=reuse hermes-web-ui · B=in-repo thin UI · C=ship v1.0 with no UI ·
D=full Vue SPA in-repo).

## Decision

### 1. Replace §6.1.4-§6.1.7 with an in-repo, server-rendered thin UI

- Mount under `/ui` (server root `/` keeps redirecting to docs / OpenAPI).
- **Stack**: FastAPI + Jinja2 templates + a single hand-written
  `app.js` (~150 lines, no build step, no npm).
- **Pages**:
  - `GET /ui` — task list + new-task form
  - `GET /ui/tasks/{task_id}` — task detail + live event log
    (`EventSource('/tasks/stream' + manual replay`) + `resume` form when
    `awaiting_user`.
- **Status display**: 12 UI labels are derived client-side per ADR-0011's
  mapping table. The 4-state `TaskResult.status` + the most recent
  `Event` + (when present) the latest `ReviewerDecision` are the only
  inputs.
- **Streaming**: `EventSource('/tasks/{task_id}/stream')` (new GET
  variant of the existing POST stream — POST is preserved, GET is added
  for the `<EventSource>` API which only does GET). On reconnect the
  client refetches `GET /tasks/{task_id}` for a snapshot.
- **No JS framework, no build chain**: we deliberately ship a static
  `app.js` so `pip install -e .` is the entire setup.

### 2. Drop §6.1.4-§6.1.7 in PLAN.md §8 and replace with §6.1.4'-§6.1.6'

- §6.1.4' — Jinja2 templates + `app.js` SSE client + 12→4 status
  derivation (1.5d)
- §6.1.5' — FastAPI routes for `/ui` and `/ui/tasks/{id}` + GET stream
  variant + UI route tests (0.5d)
- §6.1.6' — `examples/ui_smoke.md` + screenshot + reconciliation doc
  closing entry (0.5d)

Estimate: **~2.5d** vs the prior **~4.5d**.

### 3. CLAUDE.md §1 non-goal "no UI framework" is preserved

The non-goal forbids *building a UI framework*, not *shipping a
reference UI*. The in-repo UI is explicitly framed as a developer /
demo surface. Production users are still expected to build their own
SPA against the documented API (OpenAPI is generated by FastAPI for
free). README must say this in plain text so the framing doesn't drift.

### 4. ADR-0011's state mapping is unchanged

The 12→4 derivation table in ADR-0011 §2 is the contract for any UI
client, including this in-repo one. ADR-0012 only changes *who renders
it*. The mapping survives ADR-0012 verbatim.

### 5. hermes-web-ui is no longer a v1.0 dependency

`docs/v1.0-vue-ui-reconciliation.md` and the `/api/agent-room/*`
compatibility surface (sessions thin shell) **stay** for users who want
to bring their own SPA, but the project no longer commits to that
client's specific shape. ADR-0011 §1 (`sessions = tag, not lifecycle
owner`) and the state mapping remain the public contract; whether
hermes-web-ui catches up to that contract is the consumer's call, not
ours.

## Rejected alternatives

- **A. Reuse hermes-web-ui (the prior plan).** Two-repo coordination
  tax + the deletion is itself most of the work + independence leaks at
  the use-site. ~4.5d for a worse outcome.
- **C. Ship v1.0 with no UI.** Saves ~2.5d but turns v1.0 ("stable +
  UI") into v0.6. Swagger UI doesn't replace "show a real run with
  live events" for sales / onboarding / debugging.
- **D. Full Vue SPA in-repo.** Violates CLAUDE.md §1 "not a UI
  framework" non-goal in spirit. Costs ~5-8d. No proportional
  benefit — anyone who needs a real SPA will build their own anyway.

## Consequences

- **Independence**: the project is now end-to-end self-contained for
  development and demo; `git clone && pip install -e . && agent-room serve`
  produces a working UI at `/ui` with no npm.
- **API discipline**: writing the UI ourselves will surface unused or
  ill-shaped fields immediately; we treat that as a feedback loop
  toward a tighter v1.0 SemVer contract, not as scope creep.
- **OpenAPI is the integration surface**: production users build SPAs
  against FastAPI's auto-generated OpenAPI, not by importing our
  templates. README will say so.
- **No npm in CI**: independence-driver scope is unchanged.
  `agent_room.server.ui` adds Python files only (templates + a static
  JS file delivered as a package resource).

## Out of scope (deferred)

- WebSockets / Server-Sent-Events alternatives — SSE is the contract.
- Authentication / multi-user UI — same `/ui` for everyone; gate at the
  ingress if needed (v1.x).
- Vue/React SPA examples — left to consumer-specific work.
