## 动机

当前 4 节点流水线写死在 [graph.py](../../agent_room/graph.py)。
真实场景里有多种工作流形态：
- 单角色「直答」：`conversation → END`
- 双角色「问答 + 验证」：`developer → reviewer`
- 多评审：`developer → reviewer_security → reviewer_perf → delivery`

需要从 YAML / Python dict 读取拓扑并构建图。

## 设计 (ADR-0008)

```yaml
# graph.yaml
name: full-pipeline
entry: planner
nodes:
  planner:
    role: planner
    model: claude-sonnet-4-6
  developer:
    role: developer
    model: claude-opus-4-7
  reviewer:
    role: reviewer
    model: claude-sonnet-4-6
  delivery:
    role: delivery
edges:
  - from: planner
    to: developer
  - from: developer
    to: reviewer
  - from: reviewer
    branches:
      approved: delivery
      revision_required: developer
      need_user_decision: __end__
      _exhausted: __end__   # max_revisions 用尽时走这个
  - from: delivery
    to: __end__
```

详细 ADR 见 [docs/adr/0008-graph-spec.md](../adr/0008-graph-spec.md)。

## 风险（结案）

- **R1**：YAML 表达力不够 → 兜底允许在 spec 里指向 Python callable（`router: my.module.fn`）。**已支持**，dotted-path resolver 在 `agent_room/spec.py::resolve_callable`。
- **R2**：状态字段如何在 spec 中声明？v0.2 暂不支持自定义状态字段，沿用 `TaskState`。v0.3 再考虑 generic state。**未发生**——v0.3 工具系统不需要新状态字段，结论沿用 `TaskState`。

## v0.2 学到的（适用于 v0.3+）

1. **结构修复 ≠ 行为修复**：reviewer HUMAN 消息加上 task description 后离线测试都通过了，
   但真实 LLM 仍然 0% escalation。F2 的根因是 model bias 而不是 prompt 缺料；多 prompt
   不是答案，**换调用方式**（planner_gate 改为先问 questions）才是。

2. **GraphSpec 变体 > 一次性脚本**：v0.2 §2.9 实验做成 reusable 预设，复跑成本极低
   （改一个 env 变量就重跑），后续 v0.3 工具系统的 A/B 测试也应该走这个套路。

3. **provider 偶发性故障要计入预算**：DeepSeek 偶发 `OutputParserException: Unknown tool type: ''`
   命中了 3/9 个跑——任何走 `with_structured_output` 的角色都暴露在这个面上。v0.3 工具系统
   会大量用 LangChain ToolNode（也走 structured tool calling），需要同样的容错。
