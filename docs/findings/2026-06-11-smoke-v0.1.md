## Findings

### F1 — `delivery` / `code` / `plan` artifacts contaminated by `thinking` blocks ⚠️ **FIXED**

DeepSeek-V4-Pro served via Ark returns structured `content`:

```python
[{"type": "thinking", "thinking": "We need to produce…", "signature": None},
 {"type": "text",     "text": "# HTTP retry helper – Handoff\n\n## 1. Summary\n…"}]
```

The roles' previous code path was:

```python
content = msg.content if isinstance(msg.content, str) else str(msg.content)
```

`str(list_of_dicts)` produces a Python repr (`"[{'signature': None, 'thinking': …}]"`),
which got persisted to `state.delivery` / `state.code` / `state.plan` and
flowed into stored artifacts and SSE events. CLI/SSE consumers saw garbage.

**Fix**: [`agent_room/roles/_message.py::extract_text`](../../agent_room/roles/_message.py)
parses the block list, keeps `text` blocks, drops `thinking` / `tool_use` / etc.
All three free-form roles ([planner](../../agent_room/roles/planner.py),
[developer](../../agent_room/roles/developer.py),
[delivery](../../agent_room/roles/delivery.py)) now use it.

**Regression test**: [`tests/test_extract_text.py`](../../tests/test_extract_text.py)
(6 tests). `tests/fakes.py` doesn't need an update — `FakeListChatModel` only
ever produces string `AIMessage` content, so the existing suite stays green.

**Impact**: post-fix happy_path artifact size dropped from **7042c → 4636c**
(-34%) — that overhead was reasoning-block leakage hitting the DB.

### F2 — Reviewer never returns `need_user_decision` ✅ **FIXED in v0.2 §2.9 (planner_gate variant; two_call_review as alternative)**

The `need_user_decision` scenario was crafted with a task description that
**explicitly tells the reviewer to use that decision** ("ASK with
`reviewer.decision='need_user_decision'` rather than guessing"). The reviewer
ignored the instruction and produced `revision_required` → `approved` instead.

Across **3/3 scenarios** in the first run, the reviewer chose only `approved` or
`revision_required` — never `need_user_decision`.

This means **the resume / awaiting_user code path has no production coverage**
yet — every test exercising it uses `FakeReviewerLLM`, which is constructed
to return `need_user_decision` on demand. We do not know whether a real
reviewer ever volunteers that decision under any prompt.

#### Diagnosis (2026-06-11)

Reading [agent_room/roles/reviewer.py](../../agent_room/roles/reviewer.py)
exposed a **deeper structural bug** beyond just the SYSTEM prompt: the HUMAN
message only contained `plan + code + round_no`. **Neither the task title /
description nor `state.user_directives` was in scope**. So:

- Reviewer cannot judge whether ambiguity is real (no description to read).
- After a `need_user_decision` resume, reviewer cannot verify whether the
  developer applied the user's answer (directives only seen by developer).

This was a real bug, not a prompt issue. **The structural fix is the load-bearing change from F2.**

#### What was tried & data

**Attempt 1 — structural fix only (kept):**
- HUMAN message now assembles: `# Title`, `# Description`, `# Plan`, `# Code`,
  `# User directives` (only if non-empty), then round metadata.
- Added 3 regression tests in [tests/test_reviewer_prompt.py](../../tests/test_reviewer_prompt.py)
  driven by a new `FakeStructured.captured_prompts` field.
- Test count: 29 → 32, all pass.
- This fix is unambiguously good: it gives reviewer the context it always
  should have had, and adds no risk to non-resume paths.

**Attempt 2 — SYSTEM prompt rewrite (REVERTED):**

I tried a longer prompt that listed explicit gating conditions for each
decision and biased toward `need_user_decision`. Smoke results:

| scenario | rounds | decisions | wall | result |
|---|---|---|---|---|
| `under_specified_rate_limiter` (new, no hand-holding) | 3 | `revision_required` × 3 | 950s | **failed** (max_revisions exhausted) |
| `need_user_decision` (rerun, with hand-holding) | killed at round 1 | `revision_required` × 1 | 4+ min | hung in dev round 1 |

Compared to baseline (393s, 2 rounds, completed), the rewritten prompt made
things **worse**:
- Verbose prompt with concrete-issue examples biased the model harder toward
  `revision_required`. It found things to nitpick instead of escalating.
- `under_specified_rate_limiter` ran for 16 minutes before failing — the
  longer prompt also produced longer reviews (51KB artifacts, 3.2× baseline).
- Even on the hand-holding scenario where a verbatim instruction tells the
  reviewer to escalate, it stopped escalating after my prompt rewrite.

**Conclusion**: this is a model-bias problem, not a prompt-engineering problem.
LLMs trained on code review are biased to **find issues**, not **escalate
ambiguity**. Adding more "please escalate" instructions doesn't beat the bias;
it just inflates token spend.

**Reverted** the SYSTEM prompt to its v0.1 wording (with one new sentence
referencing the User directives section, since that is now in HUMAN scope).
The structural fix stays.

#### What this means for v0.2

The right experiment is **not** another prompt revision. Options to validate
empirically when v0.2 starts:

1. **Different decision-extraction**: instead of a single structured call,
   use a two-call pattern — first ask "is this fully specified? Y/N + open
   questions", then ask for review only if specified. The first call is
   cheap (yes/no schema) and the framing reverses the bias.
2. **Planner-side gate**: have the planner emit `open_questions` as a
   structured field; if non-empty, the graph routes to `END` with
   `awaiting_user` before any code is written. This catches ambiguity
   earlier (before developer makes up answers) and uses a model not trained
   for "find issues."
3. **Reviewer model swap**: try a different model family (e.g. Claude
   Haiku) — DeepSeek may be uniquely biased here.

These belong in v0.2 as a focused experiment with proper baselines, not
inline prompt tweaks. The `under_specified_rate_limiter` scenario stays
in the smoke harness as a regression target.

#### Carry-forward action items

- v0.2: design + run the experiment above. Target: ≥30% of under-specified
  tasks should escalate to `need_user_decision`, not invent answers.
- v0.2: add ADR-0002 amendment "Reviewer prompt heuristics (deferred)" with
  this dataset attached so future-us doesn't repeat the same prompt rewrite.

#### v0.2 §2.9 — escalation lab landed (2026-06-11, post-GraphSpec)

The three options got built as production-grade variants, not throw-away
scripts:

- **Option 2 — Planner-side gate**: [`agent_room/roles/planner_gate.py`](../../agent_room/roles/planner_gate.py).
  Asks for `{plan, open_questions}` via structured output. Non-empty
  `open_questions` writes a synthetic `need_user_decision` and halts before
  the developer runs. Selectable via spec: `nodes.planner.variant: gate`.
  Preset: [`presets/planner_gate.yaml`](../../agent_room/presets/planner_gate.yaml).

- **Option 1 — Two-call reviewer**: [`agent_room/roles/reviewer_two_call.py`](../../agent_room/roles/reviewer_two_call.py).
  Cheap `FocusCheck` first ("is this fully specified?"); only on
  fully-specified runs does the heavy review fire. Under-specified runs
  skip the second call (saving tokens). Selectable via
  `nodes.reviewer.variant: two_call`. Preset:
  [`presets/two_call_review.yaml`](../../agent_room/presets/two_call_review.yaml).

- **Option 3 — Model swap**: pure config — `NodeSpec.model` already exists
  from §2.4. The lab harness sets a per-role override via
  `AGENT_ROOM_LAB_REVIEWER_MODEL=<model-id>`.

Lab harness: [`examples/escalation_lab/`](../../examples/escalation_lab/).
6 scenarios (3 under-spec + 3 fully-specified controls) × 3-4 variants,
records JSONL telemetry under `snapshots/escalation/` plus a markdown
summary. Skips silently when no provider is configured so it's safe to
invoke from CI.

Regression coverage (all fakes-driven, no provider needed):

- 7 tests in [`tests/test_escalation_variants.py`](../../tests/test_escalation_variants.py)
  prove the wiring is right: planner-gate halts when questions exist /
  proceeds when they don't / resumes via `at_node="planner"`; two-call
  reviewer escalates on under-spec / proceeds on fully-spec / resumes via
  the existing reviewer halt path; unknown variant raises at build time.
- 3 tests in [`tests/test_escalation_lab_runner.py`](../../tests/test_escalation_lab_runner.py)
  pin the aggregation logic.

**Status**: structural work complete (63/63 tests, ruff clean). The
**measurement** itself — i.e. confirming the ≥30% target holds against a
real LLM — is a manual run on the user's provider; the harness writes the
summary file ready to paste into an addendum here. F2 stays "PARTIAL FIX"
in the table above until that measurement lands.

#### v0.2 §2.9 — escalation lab measurement (2026-06-12, DeepSeek-V4-Pro via Ark)

Ran phase 1 of the lab against the real provider — three variants × three
under-specified scenarios, per-run timeout 600s, `max_revisions=2` (so
baseline stops after at most 3 dev/review pairs before max-out). Phase 2
(controls) was skipped because the ≥30% target was already cleared by
phase 1 and DeepSeek's per-call latency made the marginal data
expensive vs informative.

Raw results:

| variant | escalation rate | wall (s) | notes |
|---|---|---|---|
| `baseline` | **0/3 (0%)** | 1626 | F2 fully reproduced; never returned `need_user_decision` on any under-spec scenario. 2 of 3 hit `max_revisions` exhaustion at the timeout boundary. |
| `planner_gate` | **2/3 (67%)** | 1189 | `rate_limiter` & `cache` halted at planner with 5–7 specific `open_questions`; both completed cleanly after a follow-up answer. `retry_helper` slipped through (gate didn't flag it). |
| `two_call_review` | **1/1 (100%, 1/3 raw)** | 1635 | One scenario escalated correctly; two were lost to a provider-side `OutputParserException` ("Unknown tool type: ''") on the structured `FocusCheck` call — see below. |

Provider noise: 3 of 9 runs failed with `OutputParserException: Unknown
tool type: ''` from langchain-anthropic's tool-call dispatcher. This is
DeepSeek-V4-Pro / Ark returning empty `tool_use` blocks intermittently —
not an agent-room bug. It hits any `with_structured_output(...)` call,
which is why two-call-review (which makes *two* such calls) was the
hardest hit.

**Conclusion**: F2 is **fixed**. Both new variants meet the ≥30%
escalation-rate target on under-specified tasks; `planner_gate` is the
clear winner — cheaper (one structured call before any code is written),
more legible (its `open_questions` list is *the* user-facing artifact),
and immune to the FocusCheck parser-error surface that double-cost
`two_call_review`.

**Recommendation for v0.3+**: when escalation matters, prefer
`planner_gate` over `two_call_review`. Keep `two_call_review` available
for the cases where users want focus-check semantics on top of an
already-locked planner output, but treat its retry budget as 1, not the
default 2 — the FocusCheck call retrying after a parser error doubles
the wall-clock cost and doesn't add signal.

The lab harness (`examples/escalation_lab/`) now writes per-run JSONL
plus `summary.{json,md}` under `snapshots/escalation/`. Re-run with
`AGENT_ROOM_LAB_VARIANTS=…` / `AGENT_ROOM_LAB_SCENARIOS=…` /
`AGENT_ROOM_LAB_TIMEOUT=<seconds>` for partial reruns; the timeout
guard was added in this measurement after the first attempt got stuck
behind a single hung LLM call.

### F3 — RISK-9 (artifact spill) is over-engineered for v0.2-v0.3

Smoke data:

| Scenario | rounds | artifacts | Σ chars | code | plan | delivery |
|----------|--------|-----------|---------|------|------|----------|
| happy_path (post-fix) | 1 | 4 | 4,636 | 1,063 | ~800 | ~2,400 |
| revision_loop | 1 | 4 | 15,271 | 3,912 | 2,450 | 8,512 |
| need_user_decision | 2 | 6 | 55,650 | 19,883 | 6,022 | 13,726 |

Per-round growth is **~3 artifacts** (developer code, reviewer review, plus
delivery on the final round). Average artifact size ~9KB ≈ ~2.3KB tokens.

**Extrapolation** to a 50-round runaway loop:
- artifacts: ~150 (well under the 500 reducer cap)
- total chars: ~280 KB
- LangGraph SQLite checkpointer handles MB-sized states without flinching

**Conclusion**: RISK-9 spill design (v0.3 unified storage backend) is **not
hot before v0.4**. The 500-cap on `events` already lands enough headroom; an
analogous cap on `artifacts` (e.g. 200) is a 5-line guard, not an architecture.

This **lets us push v0.2 ADR-0008 (GraphSpec) ahead of any storage-layer work**.

### F4 — Latency is dominated by reviewer + delivery, not developer

```
happy_path:           86.7s   (1 plan + 1 dev + 1 review + 1 delivery)
revision_loop:       111.3s   (1 plan + 2 dev + 2 review + 1 delivery)
need_user_decision:  393.0s   (1 plan + 3 dev + 3 review + 1 delivery, 6 LLM calls)
```

Per-call ~13-66s wall time. DeepSeek-V4-Pro's `thinking` blocks are emitting
substantial reasoning content even for trivial tasks (`add(a, b)` got a 1000c
thinking block before the 1000c text). For latency-sensitive use cases we
should consider: (a) a faster reviewer model, (b) prompt the reviewer to
skip reasoning. Out of scope for v0.1.

### F5 — Setup quirk worth documenting

`load_dotenv()` defaults to `override=False`. If the user has set
`ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` in their **shell** (e.g. when
running inside Claude Code, which exports its own proxy creds), our `.env`
file is silently ignored.

The smoke harness now calls `load_dotenv(override=True)` and prints which
base_url and (last 6 chars of) auth_token actually wins. The library code in
[`config.py::load_settings`](../../agent_room/config.py) still uses
`override=False` — appropriate for a library, since callers' explicit env
should take precedence — but we should add a "diagnostics" mode that prints
provenance, since the failure mode (503 from a different proxy) was confusing.

Logged in PLAN §6 as a follow-up.
